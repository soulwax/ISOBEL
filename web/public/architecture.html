How a song gets from Songbird to the voice channel

The bot pulls a 320 kbps MP3 from the Songbird API and encodes it to Opus once, then reuses that Opus file. This page follows a song from the /play command to the Discord voice channel. It covers which of the five playback paths is chosen and why, the exact ffmpeg commands, how volume and ducking work, how failures are retried, and how the file cache fills up and empties.

01System map

All playback state belongs to one Player object per guild. PlayerManager creates these on demand and keeps them in a map keyed by guild ID. Commands and Discord events only ever call methods on a Player. The Player owns the ffmpeg processes, the discord.js audio player and the voice connection.

02From /play to a queued song

AddQueryToQueue joins the voice channel and resolves the query at the same time, so a cold start doesn't wait for one before starting the other. /play asks GetSongs for exactly one result.

03How getStream() picks a path

getStream() runs on every play, seek, resume after a reconnect, and volume change on the passthrough path. It checks these questions in order and stops at the first "yes".

04The five playback paths

The decision above produces one of these five streams. The highlighted row is the one the design is built around: no ffmpeg process runs at all. The /health endpoint reports which row is in use as playbackPath.

05The ffmpeg commands

All ffmpeg processes are started through ffmpeggy and piped into an fs-capacitor buffer, which the AudioPlayer reads from. A byte counter sits between ffmpeg and that buffer to feed the telemetry (section 10). If ffmpeg hasn't sent its start event within 5 seconds, the attempt fails.

Input flags, network sources only

-reconnect 1 -reconnect_delay_max 5
-readrate 1.5 -readrate_initial_burst 15
# then, for seeks:
-ss <start> -to <end>

Songbird replies to ranged requests with at most 1 MiB per response. Without -reconnect, ffmpeg treats that as end of file and the track stops after about 26 seconds. The burst flag needs ffmpeg 6.1 or newer. This is checked once at startup, and older versions get only -readrate 1.5.

Opus output (the encode path)

-vn -c:a libopus -b:a <kbps>k
-ar 48000 -ac 2
-packet_loss 5 -fec 1
-f webm
[-filter:a volume=<0.0–1.0>]

The bitrate is the voice channel's bitrate, capped at 128k, or 64k if the channel's bitrate is unknown. The volume filter is only added when volume is below 100%.

Copy output (the remux path)

-vn -c:a copy -f webm

Trims the cached Opus file at the seek point without decoding it. Seeking costs no encode and loses no quality.

PCM output (the ducking path)

-vn -f s16le -ar 48000 -ac 2

The stream reaches discord.js as StreamType.Raw with inlineVolume: true, which is 192,000 bytes per second.

Background Opus encode

-i <cached mp3>
-vn -c:a libopus -b:a <kbps>k
-ar 48000 -ac 2 -packet_loss 5 -fec 1
-f webm   # → FileCache, key opus:<id>:<kbps>

The same settings as the live encode, so the output is identical. It runs through a pool shared by every guild that allows 2 encodes at once, and the process is set to nice 10. If the encode is cut short it is thrown away and never reaches the cache.

06Player states

Player.status has three values. A new Player starts in PAUSED. When the discord.js AudioPlayer reports Idle, the current track has ended, and this is what moves the queue forward.

07Volume and ducking

How a volume change is applied depends on the path. On the passthrough path nothing between ffmpeg and Discord can change the gain, so a volume change restarts the stream at the current position.

08File cache: warming, writing, eviction

Two kinds of file go into the cache: the source MP3, under the key mp3:<id>:320, and the encoded Opus, under opus:<id>:<kbps>. Each key is hashed to a filename. When a track starts, the bot also prepares the next track in the queue.

09What happens when things fail

Retries happen at three levels, from fast and local to slow and global. Each level only gives up after its own limit, then hands the problem to the queue by skipping the track or disconnecting.

10Telemetry

Two numbers tell a network problem apart from a CPU problem. Both are sampled every second for each guild that is playing, appear in GET /health, and are printed with DEBUG=ISOBEL:audio together with the event-loop lag.

cushionSeconds

bytesFromFfmpeg / byteRate
  − playbackDuration / 1000

byteRate = kbps × 1000 / 8    # Opus
byteRate = 192 000             # PCM

How far ffmpeg is ahead of the listener. It should climb toward 15 s after a track starts. If it stays near zero, the input is being read at real-time speed and any network hiccup will be heard. It shows null on the cached-file path, where there is no ffmpeg to measure.

lostPlaybackMs

Σ max(0, wallElapsed − played)

Wall-clock time during which playback didn't advance, which is audible stutter. If this grows while the cushion is healthy, the cause is the event loop, not the network. Background encodes are capped and niced for this reason.

Position

positionAtStreamStart
  + floor(playbackDuration / 1000)

Position comes from how much audio has actually played, not from the wall clock. A stall therefore can't push the progress bar or a later seek(position) ahead of what the listener heard.
